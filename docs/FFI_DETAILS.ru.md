# FFI: объявления, DLL, указатели и callbacks подробно

Сначала прочитай [FFI.ru.md](FFI.ru.md): подключение модуля, первые вызовы,
буферы, динамические текстуры и границы исполнения. Здесь разобраны договор
с собственной DLL, пути Windows, завершение ресурсов и типичные ошибки.
Полный перечень вызовов — в [API_INDEX.ru.md](API_INDEX.ru.md).

## Как выбрать интерфейс DLL

FFI вызывает функции, которые реально экспортирует библиотека. Декларация
в `ffi.cdef` описывает способ вызова; она не создаёт функцию в DLL и не
проверяет автоматически, что объявление совпадает с её исходным заголовком.
Нужны имя экспорта, тип результата, типы аргументов, соглашение о вызовах,
владение указателями и правила работы с потоками.

Для своего расширения удобен небольшой C-интерфейс:

- Имена через `extern "C"` и экспорты `__declspec(dllexport)` в Windows.
- Простые числа, указатели на буферы и явно переданные размеры.
- Отдельные операции создать/использовать/закрыть, если есть состояние.
- Копирование результата в буфер вызывающего, если результат временный.
- Код ошибки и функция получения текста ошибки.
- Отсутствие C++ исключений, выходящих через границу экспорта.

Не объявляй `std::string`, `std::vector` или C++ класс как будто это C-строка
или плоский массив. Их внутреннее представление не становится интерфейсом
FFI. Если библиотека предоставляет только C++ классы, нужен подходящий
экспортированный C-интерфейс или отдельная обёртка. FFI сам её не генерирует.

## Типы Windows x64

| C-тип | Размер в Windows x64 | Как использовать |
|---|---|---|
| `int8_t` / `uint8_t` | 1 байт | Знаковый / беззнаковый байт |
| `int16_t` / `uint16_t` | 2 байта | Короткие значения; UTF-16 элементы в примерах |
| `int32_t` / `uint32_t` | 4 байта | Явные 32-битные поля |
| `int64_t` / `uint64_t` | 8 байт | Явные 64-битные поля |
| `int` / `unsigned int` | 4 байта | Обычные C-целые этой платформы |
| `long` / `unsigned long` | 4 байта | Не заменяют 64-битное значение |
| `size_t` / `uintptr_t` / `intptr_t` | 8 байт | Размеры и целые, соответствующие размеру указателя |
| `void*` и другие указатели | 8 байт | Адрес, а не значение по этому адресу |
| `float` / `double` | 4 / 8 байт | Два разных типа числа с плавающей точкой |

Это таблица для целевой Windows x64, а не правило для всех ОС. Для проверки
есть `ffi.sizeof`, `ffi.alignof`, `ffi.offsetof`, `ffi.abi("64bit")` и
`ffi.abi("win")`. WinAPI `BOOL` — 32-битное целое; C/C++ `bool` не нужно
подставлять вместо него. Для Windows-функций сохраняй правильное объявление
`__stdcall`, даже если на x64 применяется единое соглашение вызова платформы.
Для произвольной структуры сверяй размеры/смещения с её настоящим заголовком.
Случайно совпавший `sizeof` не доказывает правильность всего интерфейса.

### 64-битные значения

Используй `ffi.tonumber` для преобразования числового `cdata`. Преобразование
в обычное число может потерять точность для больших значений; не превращай
произвольные адреса и 64-битные идентификаторы в число лишь для удобства.
Время жизни объекта и размер адреса после преобразования не проверяются FFI.

## Пример интерфейса собственной DLL

Ниже исходник самостоятельного учебного расширения. Автор собирает его
сам как DLL **x64** и размещает по указанному пути. Этот исходник не включён
в проект скита и не был собран или исполнен в рамках офлайн-проверки.

```cpp
#include <cstdint>

using visitor = int (*)(int value, void* context);

extern "C" __declspec(dllexport)
int64_t script_sum(const int32_t* values, uint32_t count) noexcept {
    if (!values || count > 1024) return 0;
    int64_t sum = 0;
    for (uint32_t i = 0; i < count; ++i) sum += values[i];
    return sum;
}

extern "C" __declspec(dllexport)
int script_visit(visitor callback, void* context) noexcept {
    if (!callback) return 0;
    for (int i = 1; i <= 5; ++i) {
        if (callback(i, context) == 0) return 0;
    }
    return 1;
}
```

Lua-часть:

```lua
local ffi = require("ffi")
ffi.cdef[[
    int64_t script_sum(const int32_t* values, uint32_t count);
    typedef int (*script_visitor)(int value, void* context);
    int script_visit(script_visitor callback, void* context);
]]
local library = ffi.load("C:/my-plugin/script_example.dll")
local values = ffi.new("int32_t[3]", {10, 20, 30})
local result = ffi.tonumber(library.script_sum(values, 3))
print("Sum:", result) -- 60, если DLL собрана с этим интерфейсом

local visited = 0
local callback = ffi.cast("script_visitor", function(value, context)
    visited = visited + 1
    return 1
end)
library.script_visit(callback, nil) -- только синхронно; callback не сохраняется
callback:free()
print("Visited:", visited)
```

Здесь `values` живёт на протяжении вызова, DLL не сохраняет его указатель,
а размер массива соответствует `count`. Callback вызывается синхронно пять
раз в том же потоке и освобождается после завершения вызова. Не вызывай
ошибку из callback в данном примере: C++ экспорт `noexcept` не допускает
исключение через свою границу. Для прикладной библиотеки отдельно проектируй
ошибки и поведение при отказе callback, а не полагайся на этот учебный шаблон.

## Указатели и память

```lua
local ffi = require("ffi")
local bytes = ffi.new("uint8_t[8]")
ffi.fill(bytes, 8, 0)
ffi.copy(bytes, "ABCD", 4)
assert(ffi.string(bytes, 4) == "ABCD")

local address = ffi.cast("void*", bytes)
assert(address ~= ffi.nullptr)
assert(ffi.sizeof(bytes) == 8)
```

`ffi.new` создаёт объект, которым владеет Lua. `ffi.cast` меняет представление
или тип доступа; он не выделяет копию памяти, на которую указывает результат,
и не подтверждает существование адреса. Удерживай исходный объект, пока адрес
используется библиотекой. `ffi.copy`/`ffi.fill` не должны выходить за размер
выделенного буфера. `ffi.string(ptr, n)` требует не меньше `n` доступных байт.

| Кто выделил память | Кто должен освободить |
|---|---|
| `ffi.new` | Lua; не передавай эту память в чужой `free` |
| DLL через собственную функцию создания | Соответствующая функция освобождения той же DLL |
| Система через функцию Windows | Указанная в документации Windows функция |
| DLL вернула заимствованный указатель | Не освобождать самостоятельно; копировать до окончания срока жизни |

Не смешивай `malloc/free`, `new/delete` и разные CRT/DLL. Указатель,
возвращённый DLL, может перестать быть действительным при следующем вызове,
смене кадра или закрытии её объекта. Если нужна постоянная копия результата,
сделай её до этого момента. Проверяй NULL через `ffi.nullptr`.

### Освобождение ресурса

Предположим, DLL действительно экспортирует эти две функции и обещает,
что её `release` можно безопасно вызвать синхронно при выгрузке:

```lua
local ffi = require("ffi")
ffi.cdef[[
    void* script_resource_create(void);
    void script_resource_release(void* resource);
]]
local library = ffi.load("C:/my-plugin/resource_example.dll")
local handle = library.script_resource_create()
if handle == ffi.nullptr then error("Cannot create resource") end

local retained_library = library
handle = ffi.gc(handle, function(resource)
    retained_library.script_resource_release(resource)
end)

local function close_resource()
    if not handle then return end
    local resource = handle
    handle = nil
    ffi.gc(resource, nil)
    library.script_resource_release(resource)
end
events.on("shutdown", close_resource)
```

Этот пример не объявляет существующую функцию Windows или скита: он показывает
контракт для собственной DLL. Финализатор удерживает библиотеку, а явная
очистка снимает финализатор, чтобы не вызвать освобождение второй раз.
После обычной ошибки callback `shutdown` может быть пропущен. Если DLL хранит
рабочие потоки или callbacks, простого `release` в таком виде недостаточно:
нужен протокол остановки и окончания доступа к памяти.

## Callback и рабочий поток

`ffi.cast("тип указателя на функцию", function(...) ... end)` создаёт callback.
Сохраняй этот объект отдельно, пока DLL может его вызвать. `callback:free()`
освобождает его ресурсы; после этого нативный код не должен обращаться
к указателю. `callback:set(fn)` заменяет Lua-функцию существующего callback.

Variadic callbacks (`...` в C-прототипе) cffi-lua не создаёт. Это отдельное
ограничение от вызова variadic функций DLL. Во [внешнем примере PrBoom](games/DOOM.ru.md)
используется адаптер только фиксированного префикса под подтверждённый Win64 ABI:
он принимает уровень/строку формата и игнорирует все дополнительные аргументы.
Он не форматирует printf-сообщение и не добавляет общей поддержки `...`.
Не переносить такой адаптер на другую платформу без проверки ABI и контракта.

Даже синхронный callback выполняется внутри текущей фазы Lua. Если внешний
вызов происходит в `paint`, callback не получает право менять команду через
`cmd`; если в командной фазе — не получает право рисовать через `render`.
Счётчики и общие ограничения исполнения остаются общими для этого Lua state.

Асинхронный callback из чужого потока нельзя направлять в Lua state скита.
Подходящая схема: рабочий поток DLL складывает результат в принадлежащую DLL
очередь/буфер, Lua из своего callback опрашивает эту очередь и копирует данные.
Тяжёлая обработка остаётся в DLL; копирование должно быть ограниченным
по размеру/времени. Сигнал «остановись» не равен подтверждению завершения потока.
Перед выгрузкой DLL и освобождением памяти нужен договор, исключающий
дальнейшее исполнение её кода. Сам FFI такой протокол за библиотеку не создаёт.

## Пути Windows и Unicode

`ffi.load` в нашей интеграции принимает UTF-8 и использует Unicode загрузчик
Windows. Для других функций Windows это не универсальное правило: варианты
с суффиксом `W` работают с UTF-16, варианты `A` обычно используют кодовую
страницу Windows. Не передавай Lua UTF-8 строку как `wchar_t*` через cast.

Пример получения `%LOCALAPPDATA%` как UTF-8:

```lua
local ffi = require("ffi")
ffi.cdef[[
    unsigned long __stdcall GetEnvironmentVariableW(const uint16_t*, uint16_t*, unsigned long);
    int __stdcall WideCharToMultiByte(unsigned int, unsigned long, const uint16_t*, int,
                                     char*, int, const char*, int*);
]]
local kernel = ffi.load("kernel32")
local name = ffi.new("uint16_t[13]", {76,79,67,65,76,65,80,80,68,65,84,65,0})
local wide = ffi.new("uint16_t[32768]")
local count = tonumber(kernel.GetEnvironmentVariableW(name, wide, 32768))
if count == 0 or count >= 32768 then error("Cannot read LOCALAPPDATA") end
local out = ffi.new("char[98304]")
local size = tonumber(kernel.WideCharToMultiByte(65001, 0, wide, count, out, 98304, nil, nil))
if size <= 0 then error("Cannot convert LOCALAPPDATA") end
local directory = ffi.string(out, size) .. "/skeet/native/"
print("Native directory:", directory)
```

Не исполняй чтение окружения и загрузку той же библиотеки заново каждый кадр.
Относительный путь DLL зависит от каталога поиска процесса; полный путь
делает выбор файла явным. Наличие файла не гарантирует, что все его зависимости
доступны загрузчику. Имена экспортов также должны совпадать точно.

## Перенос LuaJIT-скрипта

Перед переносом проверь:

1. Используются ли `jit`, `bit`, `package`, произвольный `require`, `io`, `os`:
   эти модули не предоставлены. Для побитовых операций Lua 5.5 есть операторы
   `&`, `|`, `~`, `<<`, `>>`, но переписывание нужно сверять с исходным смыслом.
2. Поле `ffi.NULL` заменить подходящим `ffi.nullptr`, а преобразование `cdata`
   выполнять через `ffi.tonumber` / `ffi.type`, когда оно требуется.
3. `cdef` должен использовать синтаксис cffi-lua. Препроцессор, bit fields,
   C++ объявления и все расширения LuaJIT не поддерживаются автоматически.
4. Зависит ли DLL/скрипт от другой архитектуры, ABI, фиксированного адреса
   или структуры движка: одной замены имени FFI для переноса недостаточно.
5. Нужны ли функции из другого игрового Lua API: cffi-lua не добавляет их
   в `render`, `client`, `entity` и остальные модули скита.

Полные особенности реализации сохранены в
[upstream API](ffi-reference/api.md),
[семантике](ffi-reference/semantics.md) и
[синтаксисе](ffi-reference/syntax.md).

## Поиск ошибки по стадиям

| Где не прошло | Что собрать и проверить |
|---|---|
| `require` / глобальный `ffi` | Версия сборки; модуль присутствует только в новой сборке |
| `cdef` | Текст объявления, синтаксис, отсутствие препроцессора, совпадение типов |
| Загрузка DLL | Полный путь, x64, зависимости, текст ошибки Windows |
| Получение `library.function_name` | Точное имя экспорта; наличие функции в DLL |
| Вызов | Типы аргументов/результата, NULL, размеры, ABI, поток |
| Чтение результата | Срок жизни указателя, размер буфера, кодировка |
| Reload / выключение | Очистка, удержание DLL, отсутствие активных callbacks/потоков |
| Падение процесса | Нативная диагностика; обычный Lua traceback может отсутствовать |

`ffi.errno` относится к C `errno`. Windows `GetLastError` — отдельный механизм;
читать его нужно по договору соответствующей Windows-функции. Не считай любое
ненулевое значение после произвольного вызова его достоверной ошибкой.

В сообщении об ошибке нужны путь/имя DLL, её версия или SHA-256, точный `cdef`,
минимальный Lua-код, входные данные и момент сбоя. Для собственной DLL приложи
описание владения памятью и callback. Декларация, которая просто разбирается
без ошибки, ещё не проверенный нативный интерфейс.
