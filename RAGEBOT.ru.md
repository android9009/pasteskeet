# Lua API v2: расширение рейджбота

## Два способа работы

1. **Изменение стадий штатного рейджбота.** `rage_targets`, `rage_scan`, `rage_select`, `rage_fire` получают копии данных. Возвращаемая таблица заменяет результат конкретной стадии. `nil` сохраняет встроенный вариант. Отдельно можно заменить точки только головы, выбрать свой способ ранжирования попаданий или запретить выстрел.
2. **Собственная логика команды.** `ragebot.claim_command()` в `pre_rage` исключает штатный рейджбот из текущей команды. Скрипт использует `entity`, `combat`, `trace`, `math` и `cmd` для собственной логики. Это требует самостоятельного управления наведением и атакой. Функция не переносит штатный алгоритм выстрела в Lua.

Это расширенный доступ к стратегии рейджбота, **не произвольная перезапись всех его внутренних структур**. Lua не получает указатели, не изменяет bone-cache, не создаёт серверные записи и не заменяет внутренности prediction/penetration. Для изменения всех алгоритмов на уровне движка одного этого интерфейса недостаточно. Такое ограничение явно отделено от замены стратегии выбора цели и точек.

Без подписок на новые события проходят прежние ветки кода: создание JSON и вызовы Lua пропускаются. Без `claim_command()` управление остаётся штатным. Наличие подписки само по себе не меняет результат: нужен ненулевой ответ обработчика.

## Порядок

```text
create_move → pre_rage → begin_command
  → сбор доступных целей → rage_targets
  → сканирование нескольких целей/записей/позиций глаза
       → штатные точки → rage_scan → penetration
  → rage_select → штатные проверки готовности/остановки/прицела
  → rage_fire → штатное формирование выстрела
post_rage → остальная обработка команды
```

Одна команда может содержать несколько вызовов каждой стадии, включая подготовительные сканы будущего положения. Событие не означает «один раз за тик». `rage_fire` вызывается перед последующими проверками истории и коррекции выстрела: оно не подтверждает фактический выстрел. Для наблюдения за каждым выстрелом штатного рейджбота используй `rage_shot`.

### Согласование со штатным выстрелом

После формирования штатного выстрела поздние callbacks (`post_rage`, `pre_legit`, `post_legit`, `post_move`, `finalize_command`) не могут менять его время истории, индекс начала атаки и биты первичной/вторичной атаки. `cmd.set_history_ticks` и `cmd.clear_subticks` в такой команде ничего не меняют; `cmd.set_attack_start` возвращает `false`, а `cmd.add_subtick` с атакой возвращает `false`. Остальные биты в смешанной маске `cmd.set_button`/`cmd.set_button_state` остаются доступны. `cmd.get().angles` в финальном callback показывает углы сформированного выстрела. Для отмены выстрела используй `{cancel=true}` из `rage_fire`; для собственного формирования команды — `ragebot.claim_command()` в `pre_rage`.

Штатный скан головы проверяет центр, верх/боковые края, промежуточные точки вдоль наклонённой капсулы и внутренний контур. Дополнительные углы покрывают промежутки между прежними точками и нижнюю дугу повёрнутой головы. Подробный штатный скан генерирует до 96 дополнительных точек; это не обещание проверить каждую из них: лимит world-трассировок остаётся общим для целей и записей. При масштабе выше 98% добавляются точки ближе к границе капсулы, с отступом не меньше 0,5% от опорного контура. Точки определяются по геометрии текущей записи, а не фиксированной высоте над игроком. При `head scale == 0` остаётся центр; положительный масштаб задаёт удаление дополнительных точек от центра.

Для головы `combat.hitchance` и `ragebot.hitchance` исключают выборки, в которых луч раньше головы пересекает другой хитбокс той же цели. Это геометрическая оценка: она не выполняет отдельную world/penetration-трассировку для каждой выборки и не подтверждает серверное попадание. При едва открытом крае головы вероятность может быть низкой даже при найденной точке; скрипт не должен искусственно трактовать её как 100%.

Для производительности преобразованные хитбоксы, совпадающие penetration-лучи и уже вычисленные вероятности переиспользуются внутри команды. Геометрия скана используется и при выборе точки; изменение inaccuracy или spread требует новой оценки вероятности. Штатное ранжирование использует 32 выборки для предварительного отбора, затем 256 для проверки максимум 12 точек на запись с резервом под тело. Предварительная оценка не разрешает выстрел; она может изменить, какие точки доходят до полной проверки. Lua-выбор через `rage_select` проверяется отдельно и сохраняет собственный порядок.

Если прямой выстрел в центр головы проходит все 256 геометрических выборок, штатный текущий скан прекращает дополнительные проверки её контура для этой записи и этого глаза. Точки тела остаются доступны. Для простреливаемого центра, подготовки будущей позиции, No Spread и списка точек, заменённого через `rage_scan`, это сокращение не применяется. У закрытой или недостаточно надёжной головы скан продолжает поиск краёв. Результат 256/256 относится к локальной геометрической модели и не гарантирует серверное попадание.

В подробном текущем скане между основными точками головы и её уточняющим контуром проверяются выбранные центры таза, верхней груди и одной ноги. Это сохраняет шанс найти точку тела при ограниченном бюджете лучей. При Lethal Baim, принудительном Body Aim, подготовке будущей позиции и замене точек через `rage_scan` порядок не перестраивается.

## `rage_shot(shot)` — жизненный цикл выстрела

Это событие только для чтения. Оно появляется после того, как штатный `fire_gun` выставил атаку в команде; подписка не меняет алгоритм рейджбота. Для одной попытки последовательно приходят статусы с одинаковым `id`:

| `status` | Значение |
|---|---|
| `command` | Рейджбот сформировал команду атаки. Это ещё не серверное подтверждение выстрела. |
| `fired` | Для ожидающей попытки найден локальный игровой `weapon_fire`. |
| `hit` | После подтверждения выстрела найден `player_hurt` от локального игрока по выбранной цели. |
| `miss` | За 1,35 секунды после `fired` не найдено подходящего `player_hurt`; это **оценка**, а не точный вердикт сервера. `reason = "no_hurt_event"`. |
| `unconfirmed` | Не найден `weapon_fire` за 2 секунды (`no_weapon_fire`), попытка вытеснена из очереди (`overflow`) или завершена игровая сессия (`session_reset`). |

Каждый `id` уникален в текущей сессии DLL. Поля `command_number`, `command_tick`, `target_id`, `record_tick`, `hitbox`, `requested_hitbox`, `expected_damage`, `hitchance`, `forced`, `no_spread` относятся к выбранному рейджботом выстрелу. `target_id` и `victim_id` — индексы controller, как в `entity.get`; `victim_id` бывает только у `hit`. `hitbox` — выбранный для сканирования хитбокс, **не подтверждённая кость попадания**. `hitchance` передаётся в процентах. В `miss` и `unconfirmed` также есть строка `reason`.

Игровые `weapon_fire` и `player_hurt` не содержат идентификатора команды. API сопоставляет их с ожидающими попытками по времени, порядку и `target_id`; при быстрых выстрелах, ручной стрельбе или задержке событий соответствие может быть неточным. Для точного числа команд считай `command`, для подтверждённых выстрелов — `fired`. `rage_shot` не создаётся для ручной стрельбы или для полностью пользовательской атаки через `cmd`.

```lua
local shots = {}
events.on("rage_shot", function(shot)
    if shot.status == "command" then
        shots[shot.id] = {target = shot.target_id, hitbox = shot.hitbox}
    elseif shot.status == "hit" or shot.status == "miss" or shot.status == "unconfirmed" then
        print(string.format("shot %d: %s", shot.id, shot.status))
        shots[shot.id] = nil
    end
end)
```

Для изменения настроек используй `settings.override(category, name, value)` в `pre_rage`. Внутри `rage_*` запись `settings.set`, `settings.override` и изменение биндов запрещены: текущий проход должен видеть согласованные настройки. Чтение разрешено. Обычные command/combat-запросы внутри этих четырёх событий недоступны; необходимые данные уже переданы в контексте. Исключение — специализированный `ragebot.hitchance` в `rage_select`.

Все `id` игроков — индексы controller, как в `entity.get(id)`. Номера элементов массивов — **с 1**, hitbox index — **с 0**. Координаты мировые, расстояния в единицах игры, углы в градусах, hitchance в процентах. `phase` генератора узоров и углы `render.arc` — в радианах.

## `rage_targets(context)`

Контекст:

| Поле | Значение |
|---|---|
| `targets` | До 13 кандидатов, уже прошедших штатную проверку команды, здоровья, иммунитета, расстояния и наличия записей |
| `eye` | Текущая точка выстрела `{x,y,z}` |
| `allow_fire` | Этот проход допускает выстрел либо готовит будущий |
| `weapon_type` | Номер штатной группы оружия |

Каждый кандидат: `id`, `health`, `armor`, `min_damage`, `distance`, `fov`, `in_fov`, `records`.

Каждая запись: `tick`, `time`, `origin`, `velocity`, `extrapolated`, `future`, `ducked`. Это диагностическая копия, не редактируемая запись движка.

Ответы:

- `nil` — прежний список.
- `{order={3,1}}` — оставить кандидатов 3 и 1 в этом порядке.
- `{order={}}` — исключить все цели из этого прохода.

Индекс должен существовать и не повторяться. Изменение полей полученной таблицы без возврата `order` ничего не применяет. После этой стадии сохраняются штатные бюджеты, проверка FOV, приоритизация видимых целей и ротация подробного скана: `order` не обещает, что каждый кандидат будет полностью просканирован.

## `rage_scan(context)`

Контекст передаётся для **одной цели и одной записи**:

| Поле | Тип/значение |
|---|---|
| `id`, `health`, `min_damage` | Цель и порог урона |
| `record` | Копия записи, поля описаны выше |
| `eye` | Точка начала текущего скана |
| `inaccuracy`, `spread` | Текущие параметры разброса |
| `prediction` | Подготовительный проход, а не гарантия выстрела |
| `centers_only` | Облегчённый штатный проход |
| `trace_budget` | Выделенный верхний бюджет; оставшийся общий бюджет тоже ограничивает работу |
| `hitboxes` | Вся доступная геометрия этой записи, включая хитбоксы, отключённые в меню |
| `points` | Штатные точки данного прохода |

Поля хитбокса: `index`, `bone`, `radius`, `center`, `capsule_a`, `capsule_b`, `extents`, `axis_x`, `axis_y`, `axis_z`. Позиции/оси находятся в мировом пространстве; `extents` — локальные полуразмеры. Положительный `radius` обозначает капсулу; для остальных используется ориентированный box. Геометрия использует те же данные и преобразования, что штатный скан.

Точка: `{hitbox=0, position={x=...,y=...,z=...}, center=false}`. `center` — необязательный признак для приоритетов, не подтверждение попадания.

Ответы:

- `nil` — штатные точки.
- `{points=points}` — **полная замена** списка, максимум 128 точек.
- `{points={}}` — пропустить эту цель/запись в этом проходе.

Можно копировать `context.points`, удалять или добавлять элементы, менять координаты и порядок. Для замены только головы сохрани остальные точки и добавь свою голову. Передавай только хитбоксы, существующие в `context.hitboxes`. Координаты должны быть конечными, каждая компонента в `[-1000000,1000000]`.

Порядок возвращённых точек сохраняется при подготовке трасс, но бюджет может закончиться до конца списка. Проверки пробития, min damage, FOV, force body и соответствия фактически поражённого хитбокса сохраняются. Lethal body aim также может завершить скан раньше. Для своей стратегии настрой эти параметры заранее через `settings.override` в `pre_rage`.

### `ragebot.pattern(kind, count [, rings=4 [, phase=0]])`

Возвращает массив нормализованных `{x,y}` в единичном диске.

- `kind`: `"rings"` или `"spiral"`.
- `count`: целое `1..128`.
- `rings`: целое `1..32`; реально не больше `count`, для spiral игнорируется.
- `phase`: поворот в радианах.

Кольца равномерно распределяют точки по окружностям и чередуют радиусы во входном порядке. Спираль использует золотой угол и радиус `sqrt((i+0.5)/count)`, где `i` начинается с нуля. Это самостоятельные генераторы для Lua; они не заменяют встроенный массив sampling и не меняют его коэффициенты.

Функция работает при загрузке скрипта: кэшируй узоры и пересчитывай только при изменении настроек.

### `ragebot.multipoints(hitbox, offsets [, scale=100])`

Только в `rage_scan`. Использует доверенную геометрию **текущей записи**, а не редактируемую пользователем копию `context.hitboxes`. Смещения `{x,y}` находятся внутри единичного диска; максимум 128, `scale` от 0 до 100. X направлен вправо относительно линии прицеливания, Y вверх.

Для капсулы строит точки её силуэта с учётом концов; для box — пересечения направления с поверхностью в локальных осях. Возвращает готовые `RagePoint[]`. `{x=0,y=0}` даёт центр. Масштаб относится к расстоянию от центра до поверхности. Радиусы, шаг, вращение, асимметрия и обрезка узора настраиваются самим массивом offsets.

Пример [rage_patterns.lua](examples/rage_patterns.lua) даёт отдельные кольца/спирали и масштабы для головы, корпуса и ног; остальные точки можно сохранить.

## `rage_select(context)`

Контекст: `hits`, `inaccuracy`, `spread`, `no_spread`, `required_hitchance` (0..100), `allow_force`.

Каждое попадание: `id`, `health`, `position`, `angles`, `damage`, `fov`, `hitbox` (фактический), `requested_hitbox`, `hitgroup`, `center`, `penetrated`, `eye`, `record`.

Список уже прошёл штатное сканирование и пороги урона, но ещё не прошёл штатное ранжирование и отбор top-K. Можно полностью заменить **выбор среди этих попаданий**:

- `nil` — выполнить штатный `select_best`.
- `{index=N}` — выбрать N-е попадание.
- `{index=0}` — не выбирать попадание.

Принятый индекс заменяет штатное ранжирование, включая бонус головы и порядок lethal body aim. Реальные hitchance и порог всё равно вычисляются для выбранного попадания. Возврат индекса не обходит проверку вероятности, min damage, готовности оружия, scope, autostop и запрет выстрела из будущей записи.

### `ragebot.hitchance(index)`

Только в `rage_select`. Геометрическая вероятность `0..100` для переданного попадания, его кости/записи, позиции глаза и параметров этого прохода. При активном no spread возвращает 100. Результаты кэшируются на время одного вызова стадии. Это не повторный расчёт пробития и не гарантия попадания на сервере.

До 32 запросов на скрипт за команду, совместно с `combat.hitchance`. Сначала отсортируй кандидатов дешёвым критерием, затем оцени несколько лучших. Пример [rage_selection.lua](examples/rage_selection.lua) выбирает попадание по своему критерию среди максимум четырёх проверенных кандидатов на вызов.

## `rage_fire(context)`

Контекст содержит поля одного попадания плюс `hitchance`, `required_hitchance` (проценты), `forced`. Возврат `{cancel=true}` отменяет этот выстрел; `nil` или `{cancel=false}` продолжает штатный путь. Геометрию/углы выстрела здесь менять нельзя: для этого измени точки раньше.

## `ragebot.claim_command()` — собственный алгоритм

Вызывается только в `pre_rage`. Заявка живёт до следующего `create_move`. Без повторной заявки включённый в меню рейджбот возобновляет работу. Выгрузка/ошибка скрипта снимает заявку; значения конфигурации при этом не меняются. Можно использовать режим и при выключенном штатном рейджботе.

Для собственной стратегии доступны `entity.players`, `combat.context`, `combat.records`, `combat.hitboxes`, `combat.damage`, `combat.hitchance`, `combat.can_shoot`, `combat.aim_punch`, `trace.line`, `math.calc_angle`, `cmd.set_angles`, `cmd.set_button`, `cmd.set_movement`. Пример [rage_custom_command.lua](examples/rage_custom_command.lua) показывает автономный выбор центра цели, наведение и запрос атаки без штатного rage-прохода.

Этот режим **не вызывает штатный `fire_gun`**. История hide-shots, seed correction/no-spread, backtrack commit и prediction штатного рейджбота автоматически к собственной команде не добавляются. Пример не заявляет их реализацию. Остальные функции, включая legitbot, anti-aim и movement, продолжают работать и могут влиять на команду. Для изолированного теста выключи конфликтующие функции через обычные настройки. Изменения `cmd.*` немедленные и, как в API v1, не откатываются при ошибке последующего Lua-кода. Подписки `rage_*` дают более надёжный путь для сохранения штатной механики выстрела.

## Несколько скриптов, ошибки и нагрузка

- Порядок скриптов — сортировка канонического имени файла; callbacks одного скрипта — порядок регистрации.
- Все получают исходный снимок стадии. Последний корректный ненулевой ответ побеждает; результаты не складываются. `nil` не отменяет ответ другого скрипта. Если нужны совместные изменения, объединяй их в один обработчик.
- Если скрипт ошибся, его ответы **текущего вызова стадии** отбрасываются и он выключается. Результат другого корректного скрипта сохраняется; иначе применяется штатный вариант. Уже завершённые стадии не переигрываются.
- Ошибка формата результата, недоступный индекс, повтор индекса, NaN/Inf, превышение лимита считаются ошибкой скрипта. Подписки и overrides снимаются обычным механизмом выгрузки.
- Лимит `rage_*` на скрипт/команду в обновлённой сборке: 4096 вызовов и суммарно 64 мс, включая преобразование аргументов, выполнение и чтение результата. Общий instruction budget тоже действует. Уже начатый нативный вызов нельзя прервать посередине; превышение обнаруживается после него. Это аварийный верхний предел, а не целевое время обработки каждой команды.
- Ограничения штатного скана сохраняются: до 13 целей, 2 подробных цели, 4 записей на цель, общий бюджет penetration 160. Это верхние пределы, не гарантия обработки всех точек. Восстановление алгоритма на всех 128 точках каждой цели в каждом проходе может быть слишком дорогим.
- Если несколько скриптов заявляют `claim_command`, штатный rage остаётся выключенным, а их обычные `cmd.*`-записи выполняются в порядке скриптов. Автоматического объединения двух алгоритмов нет.

Настройки `ui.create` сохраняются в `.cfg` существующим механизмом; сами callbacks, снимки, текущая заявка на команду и resource handles не сериализуются.
## R8: штатный режим и полная замена из Lua

Револьвер снова доступен штатным ragebot и legitbot. Временное отключение и предупреждение убраны. Настройки пистолетов действуют и для R8. Чтобы заменить только R8, в `pre_rage` проверяйте `combat.weapon_state().is_revolver` и вызывайте `ragebot.claim_command()` **каждую команду**, пока собственный алгоритм активен. Другие оружия продолжат использовать штатный ragebot. Для исключения второго бота выключите legitbot в настройках пистолетов либо не включайте его одновременно с собственным скриптом.

`combat.weapon_state()` возвращает `client_tick`, `tick_base`, `ready_tick` (`m_nPostponeFireReadyTicks`), `next_primary_tick`, `next_secondary_tick`, `ammo`, `reloading`, `can_start_primary`, `postponed_primary_ready`, `item_id`, `is_revolver`. Это снимок состояния текущего оружия, а не гарантия, что сервер уже произвёл выстрел. `combat.can_shoot(true)` пропускает проверку `NextPrimaryAttack`, но продолжает проверять патроны и перезарядку; применять только к уже удерживаемому взводу. `cmd.get()` теперь даёт `buttons_changed`, `buttons_scroll`, `history_count`.

Для собственного взвода доступны `cmd.set_button_state(buttons.attack, held, changed, scroll)` и `cmd.set_attack_start([history_index])`. Первый вызов задаёт удержание и фронты кнопки явно; для начала взвода обычно нужен `true, true, true`, для последующих удерживаемых команд — `true, false, false`, для отпускания — `false, true, false`. `cmd.set_attack_start()` отмечает последнюю запись истории как начало первичной атаки и возвращает `false`, если истории нет. При ПКМ сначала отпускайте ботскую ЛКМ и отдавайте команду альтернативной атаке. Все `cmd.*` меняют только текущую команду; состояние цикла взвода храните в Lua. Пример каркаса: [revolver_control.lua](examples/revolver_control.lua).

`cmd.set_shot_angles(angles)` доступен после `ragebot.claim_command()` в `pre_rage`: задаёт угол базовой команды и записей истории, а также сохраняет его от финального поворота anti-aim. Вызывайте только на команде действительного выстрела. Для отбора цели и коррекции разброса доступны `combat.spread_sample`, `combat.spread_correction`, `combat.hitboxes`, `combat.damage` и `combat.hitchance`. `cmd.set_history_ticks` позволяет задать player/render tick для всех записей истории, если собственный алгоритм использует backtrack; неверные значения могут привести к промаху или отклонению команды сервером.

Собственный R8-алгоритм обязан самостоятельно выбирать точку и проверять выстрел через `entity.players`, `combat.records`, `combat.hitboxes`, `combat.damage`, `combat.hitchance`, `trace.line`. `ragebot.claim_command()` не запускает штатный `fire_gun`, коррекцию No Spread, скрытые углы, backtrack commit или автопик за скрипт. Выстрел до завершения игрового взвода R8 невозможен; `ready_tick` нужно сверять с фактическим расходом патрона в `combat.weapon_state().ammo` либо с игровым событием. Не считайте вызов `cmd.set_button_state` подтверждённым выстрелом.
